# 望道项目协作规则

## 适用范围与阅读顺序

本文件适用于仓库根目录及全部子目录，是本项目唯一的代理规则，供两位项目成员及其 AI 共同使用。

开始工作时依次阅读：

1. `AGENTS.md`：协作、运行、记录和提交规则。
2. `README.md`：仓库入口、当前主线、关键结果和常用命令。
3. `PLAN.md`：完整事实、阶段目标、已完成事项和下一步计划。

正式代码、数据入口、权重和结果都以当前仓库为准。外部工程只能作为只读参考；除非用户明确要求，不得修改，也不得成为运行时依赖。

## 目录规则

- `data/`：正式数据和唯一索引。
- `materials/`：立项书等本地材料；含个人信息的内容不得提交 Git。
- `software/`：Python 模块、入口脚本、测试和正式冻结权重。
- `hardware/`：RTL、测试平台、驱动和 Vivado 工程。
- `results/`：可长期追溯的正式 JSON 结果。
- `results/runs/`：训练过程、探索实验、日志和 checkpoint，Git 忽略。
- `tmp/`：未分类临时内容，Git 全部忽略。

不要为单个文件新建目录，不提前创建没有实现内容的多级结构。新增内容优先放入现有模块；只有形成长期独立职责时才增加子目录。

## 文档规则

- 文档只保留当前有效事实、必要结论和可执行信息，不记录代理的思考过程、修改过程或已经被替代的措辞。
- 修改方案后直接写最终方案，不使用“无某方案版”“原方案修改版”等过程性命名。失败实验只有在影响技术决策或防止重复踩坑时才保留简洁结论。
- 全仓库只维护必要文档：`README.md` 负责快速入口和当前状态，`PLAN.md` 负责完整路线与阶段进度，`AGENTS.md` 负责协作规则。优先更新这三个文件，不新增零散说明。
- 完成有意义的阶段推进后，同步更新相关文档；普通命令、临时排查和没有改变结论的运行不触发文档更新。
- 不允许文档长期保留已失效状态。更新时检查当前主线、已完成事项、正在进行事项、下一步和关键结果是否一致。
- 文档应让不了解项目的队友或 AI 无需通读全部源码即可明确项目目标、数据边界、目录职责、当前模型、关键结果和下一步任务。
- 注释只解释必要的接口契约、算法约束和不直观原因，不复述代码，不写临时调试经过。

## 数据与实验记录

- 正式数据只允许读取 `data/EV-UAV-dataset/`。
- Train-main 用于训练，Train-dev 用于调参，HW-calibration 用于量化和硬件校准，Validation 用于冻结后的阶段评测，Test 仅用于最终验收。
- 模型、阈值、位宽和后处理冻结前不得运行 Test，也不得根据 Test 调整方案。
- H2 是 ANN 基线和蒸馏教师，不能写成 SNN；软件、仿真、综合和 FPGA 实测结果必须明确区分。
- 不覆盖已冻结权重。正式小型冻结权重可以提交；训练 checkpoint、大日志和临时权重只能放入 `results/runs/`。
- 每次有研究意义的运行都保存一份结构清晰的 JSON。包括训练、模型推理、结构对比、量化扫描、近似计算评测、综合和板级实验；语法检查、静态检查、帮助命令和普通文件操作无需记录。
- 正式结果放在 `results/`；探索、冒烟和训练过程放在 `results/runs/`。同一次训练的逐轮指标写入同一个 JSON 数组，不为每个 epoch 新建结果文件。
- 新增正式实验 JSON 的顶层统一使用 `schema_version`、`status`、`experiment_id`、`stage`、`data_role`、`primary_metrics`、`decision` 和 `conclusion`；阶段特有的详细配置与结果继续按需保存。训练过程在同一文件中增加 `history` 数组。历史 JSON 不为统一格式而批量改写。
- 需要复现时再记录命令、代码提交、环境、数据索引和权重标识。只记录与判断有关的信息。
- SHA-256 只用于数据索引、冻结权重、正式导出物或文件传输一致性等确有追溯价值的场景，不为普通源码改动和每条短命令重复计算。

## 开发与运行

### 本次第一阶段任务的停止条件

用户明确要求：5 小时 Codex 额度耗尽时立即停止本任务，不继续启动工具、训练或后续工作；不使用额度重置，也不以额外信用额度继续。进行长段工作前检查可用额度。此约束不代表已修改账户级计费或应用设置；系统直接中止时可能无法再发送收尾消息。

- 修改前阅读相关代码并检查工作区状态，保留用户和队友已有且无关的改动。
- 一次实验只改变主要因素。软件位精确黄金模型先于 RTL，RTL 结果先于板级结论。
- 预计五分钟以内、无破坏性且不影响外部系统的短运行可以直接执行，包括小型训练、冒烟推理、相关测试和静态检查。
- 对预计几十分钟的训练、大型数据下载、依赖或环境安装、新建或升级 WSL、长时间综合等任务，开始前停止并直接给出完整命令、操作步骤、预期产物和完成后需要提供的信息，不让用户再追问一次。
- 无法准确判断耗时时，先用小样本或短配置估计，再决定自行执行或交给用户。现有 WSL 只有在任务确有需要时使用；安装或大规模配置 WSL 属于长任务。
- 不进行与当前改动无关的运行，不为了形式完整重复执行昂贵评测。
- 每次设计或启动训练时，都应先检查数据读取与 CPU 表征构建是否形成瓶颈，并默认采用不改变训练效果的等价优化，例如向量化预处理、候选间共享不可变数据、后台预取和有边界的内存缓存。优化不得改变数据划分、样本内容与顺序、随机数调用、batch 边界、标签、数值精度、损失或参数更新；可能改变数值结果的方案必须作为独立实验，不能伪装成加载优化。训练记录应保留必要的等待时间和缓存统计，用实测决定是否继续优化，不为很短的运行做复杂基准测试。

### 本机运行方法维护

- 命令因本机的 Shell、路径、解释器、权限、编码或工具版本等原因失败，并在调整运行方式后成功时，先判断该问题是否可能再次出现。可复用的方法必须及时记录，后续优先使用已经验证成功的方式，不重复尝试已知会失败的命令。
- 记录只保留适用条件、失败原因和最终验证有效的命令或操作方式，不保留逐次试错过程、无关报错输出、临时路径或敏感信息。已有方法失效时直接修正或替换，避免并列保留互相矛盾的方案。
- 项目通用命令和环境入口记录在 `README.md`；代理协作和本机命令执行约束记录在本节。一次性的业务错误、代码缺陷或不会复现的临时故障无需写入文档。
- 本机默认宿主 Shell 为 PowerShell；调用 WSL 时明确指定 `Ubuntu-20.04`，并区分 Windows 路径与 WSL 路径。优先使用 `wsl -d Ubuntu-20.04 -- <命令> <参数>` 直接执行简单命令。PowerShell 双引号会先展开传给 `bash -lc` 的 `$变量`，因此多层调用不得直接嵌入含 Bash 变量的循环；应拆成不含变量的显式命令或使用仓库内已有脚本，不再次照搬已经发生引号解析错误的命令形式。
- Windows PowerShell 5.1 会错误解析不带 BOM 且含中文的 UTF-8 脚本或按默认编码读坏中文 JSON；供本机直接执行的 `.ps1` 保持纯 ASCII，读取 UTF-8 文件时显式指定 `-Encoding UTF8`，中文说明写入 `README.md`。Vivado 2019.1 的 XSim 参数经 PowerShell 传递时不使用文件路径 plusarg；`hardware/run_simulation.ps1` 会把向量复制到忽略的固定工作目录并使用测试平台默认文件名。
- 未执行 `python -m pip install -e .` 时，仓库根目录的临时 `python -c` 命令不会自动找到 `software/wangdao`；这类只读短命令应先执行 `sys.path.insert(0, 'software')`，正式脚本继续使用其已有的仓库路径初始化，不重复尝试直接 `import wangdao`。
- Python 命令从仓库根目录运行，并优先使用 `README.md` 中已经验证的解释器和命令形式；更换环境或解释器后应同步更新该入口。

## 验证要求

- 验证强度与改动风险相称。算法、数据和公共接口改动运行相关测试；跨模块或阶段冻结时再运行完整测试和静态检查。
- 很小的文档或局部改动可以只检查内容，不强制运行完整测试。不要在每次修改后重复数据审计、全量评测或多轮哈希检查。
- 当前项目按 `pyproject.toml` 使用 Python 3.9 及以上版本和本机可用环境，不做 Python 3.6 兼容性检查，也不继承旧 Gazelle 工程的光芯片、SDK 或部署要求。
- 验证结论必须准确：本地软件运行不能写成 FPGA 实测，局部冒烟不能写成完整评测，未执行的检查不能写成已通过。

## Git 协作

- 修改前后检查 `git status`，避免覆盖用户或队友未提交的变更。
- 根级 `/archive/`、`/tmp/`、`/project_proposal/` 永久只保存在本地；任何提交、同步、推送或 GitHub 上传都不得包含这些目录及其中内容。
- 只有用户明确说出“提交”“创建提交”或同等指令时才能执行 `git commit`。修改代码、完成任务或开始下一步不代表提交授权。
- 创建提交只代表本地提交权限；未经另行明确授权，不得执行推送、拉取、合并、变基、创建拉取请求、强制推送或改写历史。
- 提交前核对暂存内容和验证结果，确认包含用户要求保留、修改或删除的全部内容，不夹带数据集、缓存、训练 checkpoint、Vivado 生成目录、日志、视频、临时文件或个人信息。
- 提交标题和正文只能使用中文，内容应详细且可追溯，准确说明：
  1. 修改了哪些模块或内容；
  2. 解决了什么问题或为什么修改；
  3. 是否改变原有行为、接口、数据或运行方式；
  4. 实际执行了哪些测试、评测或静态检查；
  5. 仍有哪些未验证事项、限制或注意事项。
- 不使用“更新代码”“修复问题”“优化项目”等无法辨认内容的空泛提交说明，不夸大未完成的验证。
- 提交后检查提交编号和工作区状态；用户只要求提交时，不自动继续推送。
